# Lymo 개발 컨벤션

## 목적과 우선순위

사람과 AI 에이전트가 Lymo를 일관되고 안전하게 개발하기 위한 공통 규칙임. 규칙이 충돌하면 다음 순서를 따를 것.

1. 현재 작업에서 사용자가 명시한 요구사항
2. 작업 대상과 가장 가까운 `AGENTS.md`
3. 승인된 ADR과 API 계약
4. 변경 가능한 현황을 기록한 [`PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md)
5. 이 문서
6. 플랫폼별 문서와 기존 코드의 반복 패턴

상위 규칙과 충돌하거나 제품 경계, OS/제공업체 정책, 라이선스, 보안을 위반해야 한다면 구현을 중단하고 선택지를 제시할 것.

## 개발 원칙

- 요청을 충족하는 가장 작고 응집도 높은 변경을 만들 것.
- 기능, 리팩터링, 대규모 포맷 변경을 한 작업에 섞지 않을 것.
- 암묵적 전역 상태, 숨겨진 부수 효과, 출처 없는 기본값을 피할 것.
- 실패를 성공처럼 보이게 하거나 지원되지 않는 기능을 유사 동작으로 대체하지 않을 것.
- 확인한 사실과 추론 또는 미검증 가정을 명확히 구분할 것.
- 공개 계약이 바뀌면 호출부, 테스트, 픽스처, 문서를 함께 갱신할 것.
- 사용자 변경을 요청 범위 밖에서 되돌리거나 재포맷하지 않을 것.

## AI 에이전트 작업 절차

### 시작 전

1. 적용되는 `AGENTS.md`, 관련 ADR, 계약, 현황 문서를 읽을 것.
2. `git status`와 관련 파일을 확인해 기존 변경을 식별할 것.
3. 요구사항을 관찰 가능한 결과와 완료 조건으로 정리할 것.
4. 변경 범위와 검증 방법을 정한 뒤 구현할 것.

### 구현 중

- 생성 코드와 외부 의존성 코드를 직접 수정하지 말고 생성 원본이나 설정을 수정할 것.
- TODO에는 이유, 해제 조건, 추적 이슈 중 가능한 정보를 포함할 것.
- 다른 작업자가 쉽게 이해할 수 있는 이름, 작은 함수, 명시적인 상태를 사용할 것.
- 기존 변경과 충돌하면 임의로 덮어쓰지 말고 중단할 것.

### 완료 후

- 변경 내용과 이유, 실행한 검사와 결과, 미검증 사항, 남은 위험을 보고할 것.
- 실행하지 않은 검사를 통과했다고 표현하지 않을 것.
- 검사를 실행하지 못했다면 이유와 재현 가능한 명령 또는 절차를 제공할 것.

### 결정을 요청할 상황

- 해석에 따라 데이터 모델이나 사용자 경험이 크게 달라지는 경우
- 새 프레임워크, 유료 서비스, 외부 제공업체 또는 라이선스를 도입해야 하는 경우
- 인증, 권한, 개인정보, 결제 또는 삭제 범위가 불명확한 경우
- 문서화된 플랫폼 제한을 우회해야 요구사항을 흉내 낼 수 있는 경우
- 실제 기기 검증 없이 OS 통합 동작을 제품 기능으로 확정해야 하는 경우

## 아키텍처와 모듈 경계

- 현재 기술 스택과 지원 범위는 [`PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md)와 승인된 ADR에서 확인할 것.
- UI, 애플리케이션 유스케이스, 도메인, 데이터/통합 책임을 분리할 것.
- 도메인 계층에 UI 프레임워크나 외부 SDK 타입을 노출하지 않을 것.
- 플랫폼 SDK 객체와 제공업체 응답을 경계에서 내부 모델로 변환할 것.
- 의존 방향은 UI/통합에서 도메인 쪽을 향하게 하고 순환 의존성을 허용하지 않을 것.
- 플랫폼 간에는 API 계약, 픽스처, 도메인 용어, 디자인 토큰처럼 플랫폼 독립적인 산출물만 공유할 것.
- 새 모듈 구조나 크로스플랫폼 계층은 ADR로 결정할 것.

## 코드 작성 규칙

### 공통

- 식별자는 영어로 작성하고 도메인 의미가 드러나는 이름을 사용할 것.
- 짧은 인덱스를 제외하고 `data`, `info`, `manager`, `util` 같은 포괄적인 이름을 피할 것.
- 불리언은 긍정형 질문으로 읽히게 작성할 것. 예: `isImportPending`, `canObservePlayback`.
- 단위를 이름이나 타입에 드러낼 것. 예: `durationSeconds`, `positionMillis`.
- 저장 및 API 시간에는 표준과 시간대를 명시하고, 표시 형식은 UI에서 지역화할 것.
- 공개 타입과 함수에는 계약, 제약, 실패 조건을 문서화할 것.
- 매직 넘버와 문자열은 의미 있는 상수, 열거형 또는 값 타입으로 만들 것.

### Kotlin / Android

- Kotlin 공식 코딩 컨벤션과 프로젝트 포매터를 따를 것.
- Compose UI는 상태를 입력받고 이벤트를 외부로 전달할 것.
- `Composable`에서 네트워크, 저장소, 제공업체 SDK를 직접 호출하지 않을 것.
- 화면 생명주기보다 오래 유지되는 작업에 화면 또는 `Context`를 보관하지 않을 것.
- 로딩, 성공, 빈 상태, 오류, 권한 거부를 명시적인 상태 타입으로 표현할 것.

### Swift / iOS

- Swift API Design Guidelines와 프로젝트 포매터를 따를 것.
- SwiftUI 뷰는 표현과 이벤트 전달에 집중하고 네트워크나 저장 로직을 직접 수행하지 않을 것.
- 비동기 작업의 취소와 actor 격리를 고려하고 UI 상태는 적절한 메인 액터 경계에서 변경할 것.
- 실패 불가능성이 증명된 제한된 상황 외에는 강제 언래핑과 `try!`를 사용하지 않을 것.

## API, 데이터와 보안

- 계약을 구현보다 먼저 또는 같은 변경에서 정의하고 성공/실패 픽스처를 제공할 것.
- 외부 URL을 내부 식별자로 사용하지 말고 허용된 도메인과 정규화된 제공업체/리소스 ID를 사용할 것.
- 딥 링크와 알림에는 원본 URL, 곡명, 토큰 대신 불투명한 `importId`를 전달할 것.
- 서버 작업에는 인증, 권한 부여, 입력 검증, 속도/악용 제한, 멱등성을 설계할 것.
- 재시도 가능 오류와 영구 오류를 구분하고 재시도 상한, 백오프, 취소 조건을 둘 것.
- 호환성을 깨는 계약 변경에는 버전과 마이그레이션 계획을 포함할 것.
- 로그에 비밀 정보, 토큰, 쿠키, 전체 공유 URL, 전체 가사, 개인 식별 정보를 남기지 않을 것.
- 예외를 삼키지 말고 처리하거나 도메인 오류로 변환하거나 안전하게 전달할 것.

## UI와 접근성

- 비동기 화면에 초기/빈 상태, 로딩, 콘텐츠, 오류, 오프라인, 권한 거부 상태를 정의할 것.
- 권한 거부 후에도 제한된 기능을 사용하거나 설정으로 이동할 수 있게 할 것.
- 색상만으로 상태를 전달하지 말고 텍스트, 아이콘 또는 접근성 설명을 함께 제공할 것.
- 동적 글자 크기, 스크린 리더 레이블, 터치 영역, 명암 대비를 확인할 것.
- 갱신 중 사용자의 읽기 위치를 불필요하게 초기화하지 않을 것.
- AI 생성 내용과 검증된 정보를 시각적으로 구분할 것.

## 테스트와 검증

- 단위 테스트로 도메인 규칙, 정규화, 상태 전이, 오류 매핑을 검증할 것.
- 계약 테스트로 각 플랫폼과 서버가 같은 스키마와 픽스처를 해석하는지 검증할 것.
- 통합 테스트로 저장소, 데이터베이스, 네트워크 어댑터 등 실제 경계를 검증할 것.
- UI 테스트로 핵심 흐름과 오류, 권한 거부, 접근성을 검증할 것.
- 버그 수정에는 가능한 경우 회귀 테스트를 포함할 것.
- 테스트를 실행 순서, 공유된 변경 가능 상태, 실제 시각, 난수, 네트워크에 의존하게 하지 않을 것.
- 현재 PoC와 실제 기기 검증 항목은 [`PROJECT_CONTEXT.md`](PROJECT_CONTEXT.md)에서 확인할 것.
- 실제 기기 검증에는 기기, OS, 외부 앱 버전, 절차와 결과를 기록할 것.
- 시뮬레이터나 목 테스트를 실제 기기 검증으로 표현하지 않을 것.

## 의존성

- 새 의존성 추가 전 기존 의존성이나 표준 라이브러리로 해결할 수 있는지 확인할 것.
- 목적, 라이선스, 유지보수 상태, 지원 범위, 앱 크기, 개인정보 영향을 검토할 것.
- 비밀 정보는 승인된 비밀 관리 수단이나 로컬 환경 설정으로 주입할 것.
- 생성물, IDE 개인 설정, 비밀 정보, 로컬 빌드 결과를 커밋하지 않을 것.

## 문서 작성

- 사람이 한 번에 이해할 수 있는 단어와 문장 구조를 사용할 것.
- 결론과 중요한 제약을 먼저 쓰고 세부 내용은 필요한 만큼만 제공할 것.
- 중복, 장황한 배경 설명, 불필요한 제목과 예시를 제거할 것.
- 문단과 목록은 하나의 주제만 다루고 탐색하기 쉬운 제목을 사용할 것.
- 결정, 전제, 검증 방법, 위험처럼 작업에 필요한 내용은 간결성을 이유로 생략하지 않을 것.
- 같은 정보는 한 문서에서만 관리하고 다른 문서에서는 링크로 참조할 것.
- 현재 상태에는 기준일을 표시하고 변경 시 갱신 이력을 남길 것.

## Git과 PR

- 모든 변경은 `dev`에서 분기한 작업 브랜치에서 수행할 것.
- 브랜치 이름은 `<type>/<short-kebab-case>` 형식을 사용할 것. 예: `docs/agent-guidelines`.
- 커밋은 하나의 목적을 갖도록 작게 유지할 것.
- 커밋 제목은 `<type>(<scope>): <한국어 요약>` 형식으로 작성하고 `~다.`로 끝낼 것. 예: `feat(ios-import): 공유 트랙 요청을 유지한다.`
- `type`은 `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore` 중 의미에 맞게 선택할 것.
- 작업 완료 후 현재 브랜치를 원격에 푸시하고 `dev`를 base로 하는 PR을 생성하거나 기존 PR을 갱신할 것.
- `dev`와 `main`에 직접 푸시하지 않을 것.
- 사용자가 명시적으로 요청하지 않는 한 PR을 병합하지 않을 것.
- 사용자가 명시적으로 요청하지 않는 한 강제 푸시, 브랜치 삭제, 히스토리 재작성을 수행하지 않을 것.
- PR에는 변경 이유, 핵심 변경, 검증 결과, 미검증 사항과 위험을 간결하게 기록할 것.

## 의사결정 기록

다음 변경은 `docs/decisions/` 아래 ADR로 남길 것.

- 플랫폼 또는 서버 프레임워크 도입/교체
- 모듈 경계나 데이터 소유권 변경
- 외부 음악/가사/AI 제공업체 도입
- 호환성을 깨는 API 또는 저장 형식 변경
- 제품 경험, 개인정보, 라이선스 또는 비용 구조에 영향을 주는 결정

ADR에는 상태, 맥락, 결정, 대안, 결과, 검증 방법을 포함할 것.

## 완료 조건

- [ ] 요구사항과 제품 경계를 충족할 것.
- [ ] 관련 테스트와 문서를 갱신할 것.
- [ ] 오류, 오프라인, 권한 거부, 접근성을 고려할 것.
- [ ] 인증, 권한, 입력 검증, 개인정보와 로그를 점검할 것.
- [ ] 포매터, 정적 분석, 빌드, 테스트 중 적용 가능한 검사를 실행할 것.
- [ ] 필요한 실제 기기 검증을 수행하거나 미검증 상태를 명시할 것.
- [ ] 검증 결과와 남은 위험을 보고할 것.
- [ ] 작업 브랜치를 푸시하고 `dev` 대상 PR을 생성하거나 갱신할 것.
