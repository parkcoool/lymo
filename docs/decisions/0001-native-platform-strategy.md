# ADR 0001: 네이티브 플랫폼 구현 전략을 채택한다

- 상태: 승인
- 결정일: 2026-09-13
- 관련 문서: [`PROJECT_CONTEXT.md`](../PROJECT_CONTEXT.md)

## 맥락

Lymo는 Android와 iOS에서 곡을 가져와 읽고 이해하는 경험을 제공해야 한다. 두 플랫폼은 공유 수신, 앱 생명주기, 권한과 백그라운드 실행 제약이 다르다. 구현을 시작하기 전에 플랫폼 UI와 생명주기를 공유할지, 네이티브로 분리할지 정해야 한다.

이 결정은 프레임워크와 플랫폼 간 공유 범위만 다룬다. 실제 모듈 트리, 서버 런타임, 데이터 소유권과 공통 계약 형식은 아직 결정하지 않는다.

## 결정

- Android는 Kotlin과 Jetpack Compose로 구현한다.
- iOS는 Swift와 SwiftUI로 구현하고 Share Extension을 별도 플랫폼 구성요소로 둔다.
- 플랫폼 UI, 생명주기 코드와 플랫폼 SDK 타입은 공유하지 않는다.
- 플랫폼 간에는 API 계약, 픽스처, 도메인 용어와 디자인 토큰처럼 플랫폼 독립적인 산출물만 공유한다.
- React Native, Expo, Kotlin Multiplatform 등 크로스플랫폼 계층은 별도 ADR 없이 도입하지 않는다.

## 검토한 대안

### React Native 또는 Expo로 UI와 애플리케이션 코드를 공유한다

공유 코드량을 늘릴 수 있지만 Share Extension, Share Target, 권한과 생명주기 제약을 감추지 못한다. 플랫폼이 보장하지 않는 동작을 공통 추상화가 보장하는 것처럼 다룰 위험이 있어 기본안으로 채택하지 않았다.

### Kotlin Multiplatform으로 도메인 구현을 공유한다

향후 계약이 안정되면 재검토할 수 있다. 현재는 모듈 경계와 데이터 소유권이 정해지지 않았으므로 먼저 공유 계층을 만들면 검증되지 않은 구조가 고착될 수 있어 보류했다.

### 플랫폼별로 모든 산출물을 독립 관리한다

플랫폼 제약은 명확해지지만 같은 API와 상태를 서로 다르게 해석할 가능성이 커진다. 계약과 픽스처 같은 플랫폼 독립 산출물은 공유하기로 했다.

## 결과

- 각 플랫폼은 공식 SDK와 생명주기를 직접 표현할 수 있다.
- 같은 기능도 플랫폼별 구현과 테스트가 필요해 초기 작업량이 늘어난다.
- 공통 계약을 변경하면 양쪽 구현과 픽스처를 함께 검증해야 한다.
- 실제 모듈 구조는 곡 가져오기 계약 최소안과 실제 기기 PoC 결과 이후 별도 ADR로 결정해야 한다.

## 검증 방법

- Android와 iOS 실제 기기 PoC에서 플랫폼별 공유 수신과 복구 경계를 확인한다.
- 첫 모듈 구조 ADR에서 이 결정의 의존 방향과 플랫폼 독립 산출물 범위를 재검토한다.
- 현재 저장소에는 제품 구현과 실제 기기 검증 결과가 없다.
