# 제품 명세 우선 Task 운영 계획 회의

- 일시: 2026-09-13, Asia/Seoul
- 상태: 종결
- 참여: 사용자, Codex
- 관련 문서: [`PROJECT_CONTEXT.md`](../PROJECT_CONTEXT.md), [`OPEN_QUESTIONS.md`](../OPEN_QUESTIONS.md), [`ADR 0001`](../decisions/0001-native-platform-strategy.md), [`ADR 0002`](../decisions/0002-share-based-track-import.md), [Figma 와이어프레임](https://www.figma.com/design/1d8RPYFi4mCdEDyfCny83q/%EC%99%80%EC%9D%B4%EC%96%B4%ED%94%84%EB%A0%88%EC%9E%84?node-id=0-1)

## 결론

기간제 스프린트나 다단계 일정 관리 체계를 도입하지 않고, 명확한 결과와 완료 조건을 가진 GitHub Issue 단위의 Task를 한 번에 하나씩 수행한다. 첫 Task는 기술 계약이 아니라 V2 사용자 기능·화면·상태 명세와 저해상도 Figma 와이어프레임에 집중한다. 이후 곡 가져오기 계약과 iOS 우선 PoC를 진행하며, iOS 기본 경로가 플랫폼 제약으로 성립하지 않으면 Android 구현 전에 제품 방향을 재검토한다.

## 배경과 목표

기존 계획은 곡 가져오기 계약, 실제 기기 PoC와 모듈 구조 결정의 기술적 순서는 정의했지만 사용자가 체감하는 기능, 화면, 상태 명세를 별도 단계로 두지 않았다. 프로젝트에 투입 가능한 시간이 제한적이고 유동적인 상황에서 계획 체계를 과도하게 만들지 않으면서, 제품 경험을 먼저 정의하고 다음 작업을 하나씩 완료할 수 있는 실행 순서를 결정하는 것이 목표였다.

## 논의 요약

### 확인된 사실

- 현재 저장소에는 제품 구현 모듈과 실제 기기 PoC 결과가 없고, 제품 방향과 검증 계획만 있다.
- 기존 진행 순서는 곡 가져오기 계약, 실제 기기 PoC, 모듈 경계와 데이터 소유권 ADR 순이었다.
- 기존 문서에는 핵심 제품 약속과 플랫폼 제약이 있지만 MVP 기능 목록, 화면 관계와 화면별 상태를 다루는 사용자 제품 명세가 없다.
- Android와 iOS는 네이티브로 구현하며 공유 기반 곡 가져오기를 기본 경로로 사용한다.
- 사용자가 저해상도 와이어프레임을 위한 Figma 파일을 생성했다.

### 전제와 검증 필요 사항

- Figma 파일은 회의 시점에 작업 위치만 확인했으며 와이어프레임 내용과 완성도는 검증하지 않았다.
- Spotify와 Apple Music의 실제 공유 입력, iOS Share Extension과 App Group 복구 범위는 후속 Task와 실제 기기 PoC에서 검증해야 한다.
- 가사, 번역과 제공업체 데이터의 이용 조건은 실제 콘텐츠를 연결하기 전에 별도 검증해야 한다.
- iOS PoC 실패가 제품 방향 재검토 근거가 되려면 구현 결함이나 설정 오류가 아닌 플랫폼 제약임을 구분해야 한다.

## 결정 사항

1. 기간제 스프린트 대신 결과 중심 Task로 운영한다.
   - 근거: 프로젝트 투입 시간이 제한적이고 유동적이므로 기간 예측보다 하나의 결과를 완료하는 방식이 효율적이다.
   - 영향: 일정이나 완료 예정일을 두지 않고 각 Task의 완료 조건과 의존 순서를 관리한다.
   - 반영: `PROJECT_CONTEXT.md`
2. GitHub Issue 하나를 Task 하나로 사용하고 한 번에 하나만 진행한다.
   - 근거: Milestone, Project 보드와 하위 Issue를 함께 사용하면 현재 규모에서 관리 비용과 중복이 커진다.
   - 영향: 독립 추적이 필요하지 않은 작은 작업은 Task Issue 체크리스트로 관리하며 현재는 다른 일정 계층을 도입하지 않는다.
   - 반영: `PROJECT_CONTEXT.md`
3. 첫 Task는 V2 사용자 제품 명세에만 집중한다.
   - 근거: 데이터 계약과 PoC가 구현 편의가 아니라 사용자가 받아야 할 경험을 검증하도록 먼저 제품 행동을 정의해야 한다.
   - 영향: 핵심 사용자, MVP 범위, 사용자 여정, 화면·상태·행동, 플랫폼 차이, 접근성, 정보 출처 표시와 사용자 관점 완료 조건을 정한다.
   - 반영: `PROJECT_CONTEXT.md`, 후속 `product/` 명세
4. 첫 제품 명세 Task에 저해상도 Figma 와이어프레임을 포함한다.
   - 근거: 텍스트만으로 놓치기 쉬운 화면 관계와 복구 흐름을 구현 전에 검토할 수 있다.
   - 영향: 저장소의 텍스트 제품 명세를 동작의 정본으로 두고 Figma는 연결된 시각 자료로 사용한다.
   - 반영: `PROJECT_CONTEXT.md`, `docs/README.md`, Figma 와이어프레임
5. 곡 가져오기 계약 이후 iOS 공유 가져오기 PoC를 Android보다 먼저 수행한다.
   - 근거: iOS Share Extension의 입력, App Group 복구와 공유 후 복귀 경험이 기본 제품 경로로 성립하는지 먼저 확인해야 한다.
   - 영향: iOS 결과와 필요한 방향 재검토를 반영한 뒤 Android 공유 가져오기 PoC를 수행한다.
   - 반영: `PROJECT_CONTEXT.md`, `validation/plans/ios-share-import.md`
6. iOS PoC의 제품 방향 재검토 조건을 명시한다.
   - 근거: 단순 구현 오류와 제품 기본 경로를 바꿔야 할 플랫폼 제약을 혼동하지 않아야 한다.
   - 영향: 주요 앱 입력, 공식 범위 내 복구, 핵심 사용성 또는 권한·비공개 API·지원 범위 문제 중 하나가 플랫폼 제약으로 확인되면 Android PoC 전에 방향을 재검토한다.
   - 반영: `validation/plans/ios-share-import.md`
7. 콘텐츠 권리와 신뢰 모델을 실제 Reader 콘텐츠 연결 전의 독립 Task로 둔다.
   - 근거: 가사와 제공업체 데이터는 권리와 정책 검증 없이 제품 데이터로 사용할 수 없다.
   - 영향: 첫 Reader 세로 기능은 권리 문제가 없는 픽스처로 검증하고 실제 콘텐츠 연결은 검증 이후 수행한다.
   - 반영: `PROJECT_CONTEXT.md`
8. Android 재생 관찰은 기본 Reader 이후의 선택적 실험으로 둔다.
   - 근거: 공유 가져오기와 재생 관찰은 별개이며 재생 기능이 기본 읽기 경험을 막아서는 안 된다.
   - 영향: 공유, 복구와 Reader 흐름을 먼저 완성한 뒤 재생 상태·위치 신뢰도와 폴백을 검증한다.
   - 반영: `PROJECT_CONTEXT.md`

## 기각하거나 보류한 대안

- 고정 기간 스프린트: 투입 가능 시간이 유동적이어서 미완료 이월과 일정 관리 비용이 커질 수 있어 채택하지 않았다.
- Milestone, Sprint와 하위 Task 계층: 현재 프로젝트 규모와 순차 작업 방식에 비해 복잡하므로 보류했다.
- GitHub Project 보드: 진행 중 Task가 하나인 동안 별도 상태 보드의 이점이 작아 보류했다.
- 곡 가져오기 계약을 첫 Task에 포함: 사용자 경험보다 기술 구조가 먼저 고정될 수 있어 후속 Task로 분리했다.
- Android 공유 PoC 우선: iOS 기본 경로의 불확실성을 먼저 줄이기 위해 채택하지 않았다.
- 실제 콘텐츠 제공업체를 첫 Reader 세로 기능에 연결: 라이선스와 정책이 검증되지 않아 픽스처를 먼저 사용하기로 했다.

## 미결 사항

- 이번 회의에서 새로 추가한 미결 사항 없음. 기존 제공업체, 라이선스, 계약, 플랫폼과 서버 질문은 `OPEN_QUESTIONS.md`에서 계속 관리한다.

## 검증 및 근거

- `AGENTS.md`, `docs/DEVELOPMENT_CONVENTIONS.md`, `docs/PROJECT_CONTEXT.md`, `docs/OPEN_QUESTIONS.md`, ADR 0001과 ADR 0002를 최신 `origin/dev` 기준으로 재검토했다.
- 저장소가 공개 상태임을 확인하고 공개 가능한 결정, 근거, 영향과 후속 작업만 기록했다.
- Figma 파일의 존재는 사용자가 제공한 링크를 작업 위치로 기록한 것이며 내용과 접근 권한은 검증하지 않았다.
- 플랫폼, 제공업체 정책, 라이선스와 실제 기기 동작은 이번 회의에서 검증하지 않았다.
