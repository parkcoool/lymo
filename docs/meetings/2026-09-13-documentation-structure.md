# 문서 체계와 공개 원칙 회의

- 일시: 2026-09-13, Asia/Seoul
- 상태: 종결
- 참여: 사용자, Codex
- 관련 문서: [`AGENTS.md`](../../AGENTS.md), [`PROJECT_CONTEXT.md`](../PROJECT_CONTEXT.md), [`OPEN_QUESTIONS.md`](../OPEN_QUESTIONS.md), [`ADR 0001`](../decisions/0001-native-platform-strategy.md), [`ADR 0002`](../decisions/0002-share-based-track-import.md)

## 결론

일반 사용자용 얼굴 문서와 개발 문서 지도를 분리하고, 현재 확정된 플랫폼 및 곡
가져오기 경계를 두 ADR로 기록한다. 실제 기기 PoC는 계획과 결과를 분리해 증거
범위를 명확히 하며, 공개 저장소에는 정본과 정제된 근거만 남긴다.

## 배경과 목표

제품 구현 전 단계에서 필요한 문서, 기존 문서의 역할과 디렉터리 구조를 결정하고,
문서가 공개 저장소에 남아도 되는 범위를 정하는 것이 목표였다. 문서 수를 늘리는
것보다 같은 정보의 정본과 후속 결정 순서를 분명히 하는 데 초점을 두었다.

## 논의 요약

### 확인된 사실

- 저장소에는 제품 구현 모듈과 실제 기기 PoC 완료 증빙이 없다.
- 기존 정본은 `AGENTS.md`, `PROJECT_CONTEXT.md`, `OPEN_QUESTIONS.md`와
  `DEVELOPMENT_CONVENTIONS.md`로 구성되어 있었다.
- 기존 문서에는 네이티브 플랫폼 방향, 공유 기반 곡 가져오기와 실제 기기 PoC 세
  항목이 현재 방향으로 기록되어 있었다.
- 곡 가져오기 공통 계약, 콘텐츠 신뢰 모델과 실제 모듈 구조는 결정되지 않았다.

### 전제와 검증 필요 사항

- Spotify, Apple Music과 YouTube Music의 정확한 지원 URL 및 정책은 검증이 필요하다.
- 세 PoC 계획은 절차와 통과 조건이며 실제 플랫폼 지원 증거가 아니다.
- 플랫폼 구현 전략은 승인했지만 실제 모듈 경계와 데이터 소유권은 계약과 PoC 결과
  이후 결정해야 한다.

## 결정 사항

1. 일반 사용자용 루트 README와 개발자용 `docs/README.md`를 분리한다.
   - 근거: 제품의 얼굴과 내부 문서 탐색 목적이 다르다.
   - 영향: 일반 사용자에게 개발 중 상태를 명확히 알리고 개발 문서의 정본 위치를
     별도로 안내한다.
   - 반영: `README.md`, `docs/README.md`
2. `AGENTS.md`는 장기 제품 정의와 최상위 불변 경계를 관리한다.
   - 근거: 변경 가능한 현재 상태와 제품 불변 조건의 혼동을 막아야 한다.
   - 영향: 상세 설계와 검증 상태는 각 정본 문서로 이동한다.
   - 반영: `AGENTS.md`, `PROJECT_CONTEXT.md`
3. 플랫폼 구현 전략과 공유 범위를 ADR로 승인하되 실제 모듈 구조는 결정하지 않는다.
   - 근거: 프레임워크 선택은 현재 방향으로 확정되어 있지만 모듈 경계의 근거는 아직
     부족하다.
   - 영향: Android와 iOS는 네이티브로 구현하고 플랫폼 독립 산출물만 공유한다.
   - 반영: `ADR 0001`
4. 공유 기반 곡 가져오기와 재생 관찰을 서로 다른 기능으로 유지한다.
   - 근거: 공유 입력은 신뢰 가능한 재생 상태와 위치를 보장하지 않는다.
   - 영향: 모든 읽기 경험은 재생 관찰 없이도 완결되어야 한다.
   - 반영: `ADR 0002`
5. 곡 가져오기 계약 최소안, 실제 기기 PoC, 모듈 구조 ADR 순으로 진행한다.
   - 근거: 모듈 구조를 검증되지 않은 계약과 플랫폼 가정에 고정하지 않기 위함이다.
   - 영향: 일정은 두지 않고 의존 순서만 관리한다.
   - 반영: `PROJECT_CONTEXT.md`
6. 실제 기기 PoC 계획과 결과를 분리하고 공통 기록 양식을 사용한다.
   - 근거: 계획을 완료 증빙으로 오해하지 않고 과거 결과를 덮어쓰지 않아야 한다.
   - 영향: `validation/plans/`에 세 계획을 두고 첫 실행 시 날짜별 `results/` 문서를
     추가한다.
   - 반영: `docs/validation/`
7. 곡 가져오기 계약, 콘텐츠 신뢰 모델과 모듈 경계는 후속 결정으로 남긴다.
   - 근거: 계약 형식, 라이선스·출처 표현과 실제 기기 증거가 아직 없다.
   - 영향: 세 질문은 회의 출처와 함께 미결 목록에서 추적한다.
   - 반영: `OPEN_QUESTIONS.md`
8. 모든 하위 디렉터리에 README를 강제하지 않는다.
   - 근거: 설명 중복과 빈 문서의 유지 비용을 피하기 위함이다.
   - 영향: 별도 운용 규칙이 있는 `validation/`에만 로컬 README를 두고 계약 폴더는
     첫 계약 결정 시 생성한다.
   - 반영: `docs/README.md`
9. 공개 저장소에는 정본, 결정, 계약, 정제된 증거와 축약 회의록만 포함한다.
   - 근거: 커밋한 정보는 삭제 후에도 Git 기록과 포크에 남을 수 있다.
   - 영향: 사업·협상·개인정보·인증정보와 원본 증거는 공개 문서에서 제외한다.
   - 반영: `docs/README.md`, `lymo-meeting` 스킬과 회의록 템플릿
10. 개발 컨벤션은 단일 문서로 유지하고 운영 문서는 필요한 시점까지 만들지 않는다.
    - 근거: 현재 규모에서는 문서 분리가 탐색과 유지 비용만 늘린다.
    - 영향: 보안 운영서, 배포 런북과 상세 테스트 전략은 구현 구조가 정해진 뒤
      필요에 따라 추가한다.
    - 반영: 새 문서 없음

## 기각하거나 보류한 대안

- 모든 문서 디렉터리에 README 추가: 별도 규칙이 없는 디렉터리까지 설명이 중복되어
  보류했다.
- 지금 곡 가져오기 계약과 콘텐츠 신뢰 모델 확정: 제공업체 정책, 데이터 형식과 표시
  규칙 논의가 더 필요해 후속 회의로 미뤘다.
- PoC 전에 실제 모듈 구조 확정: 검증 결과가 구조를 바꿀 수 있어 보류했다.
- 서버 운영·배포·상세 테스트 문서 선행 작성: 서버와 모듈 구조가 정해지지 않아
  보류했다.
- 일정 또는 1~2주 기한 부여: 프로젝트에 투입 가능한 시간이 일정하지 않아 채택하지
  않았다.

## 검증 및 근거

- `AGENTS.md`, `docs/DEVELOPMENT_CONVENTIONS.md`, `docs/PROJECT_CONTEXT.md`와
  `docs/OPEN_QUESTIONS.md`를 최신 `origin/dev` 기준으로 재검토했다.
- 실제 기기, 제공업체 정책과 제품 구현은 이번 회의에서 검증하지 않았다.
- 새 미결 질문의 회의 출처는 저장소 검증 스크립트로 확인한다.

## 공개 범위 검토

- 공개 적합성: 확인
- 제외한 민감정보 범주: 없음
- 대화 전문이 아닌 결정, 근거, 영향과 후속 작업만 요약했다.
